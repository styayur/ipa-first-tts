## Tray callback regression, 2026-10-26

The user subsequently confirmed the browser textarea test (native t͡ʃ/œ input,
caret return and consecutive insertion) passed, but reported both actual tray
left-click and right-click had no response. This is a failed tray gate, not an
unperformed test. Publication remains held pending the fixed package retest.

The previous loop inspected only messages returned by `GetMessageW`; its window
procedure ignored the tray callback. Microsoft documents that [tray callbacks
are sent to the owning window procedure](https://learn.microsoft.com/en-us/windows/win32/shell/taskbar),
while [`GetMessage` dispatches sent messages internally before returning queued
messages](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmessage).
The fix forwards tray callbacks and the registered `TaskbarCreated` broadcast
from the procedure to separate queued events. Only the owning loop mutates App
state. Legacy notification ABI remains unchanged; mouse and keyboard activation
reveal the palette in Copy mode, and right-click/context-menu opens the menu.

A real hidden test-owned Win32 window exercises sent mouse/keyboard callbacks,
posted callback dispatch, payload retention and the registered shell recreation
message. Before the fix the first sent left-button-up callback was lost (one
test failed); after the fix this same test passed. No taskbar icon, external UI
input or Explorer restart is simulated as an actual tray pass. All 38 ordinary
Windows workspace tests and Clippy with warnings denied passed after this fix;
the three opt-in integrations retain their earlier independent run evidence.
